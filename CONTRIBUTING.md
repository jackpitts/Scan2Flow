# Contributing to Scan2Flow

Scan2Flow is at the architecture and CLI-scaffold stage. Contributions should turn a documented contract into measurable behavior while keeping the CLI and documentation consistent.

Read [DOCUMENTATION.md](DOCUMENTATION.md) before starting: it defines the current scope and next experiment. Training and model evaluation belong under `development/`, outside the installed public package.

## Local setup

Follow the platform-specific virtual-environment instructions in [README.md](README.md#installation). Install the development tools with `python -m pip install -e ".[dev]"`. See [ECC_WORKFLOW.md](development/ECC_WORKFLOW.md) for the optional ECC contributor workflow used to develop this foundation.

Create a branch from the current default branch:

```bash
git switch main
git pull --ff-only
git switch -c codex/describe-your-change
```

Use another branch name if your team requires it. Keep the change focused enough for another contributor to review without reproducing an entire research program.

## Implementation boundaries

- Keep CLI parsing and presentation in `src/scan2flow/cli.py`; place processing in the relevant domain package.
- Use typed interfaces, explicit units, and immutable stage artifacts. Do not invoke a shell with user-supplied command text.
- Preserve raw inputs. Generated outputs belong under an explicit output directory and must not overwrite existing work silently.
- Keep training and inference preprocessing shared. Never execute Python source generated by a model as a CAD program; decode a constrained representation into allowlisted kernel operations.
- Introduce optional native or GPU dependencies in isolated adapters. Document tested platform versions and lock the working backend environment before claiming reproducibility.
- Keep the application CLI-only. Notebooks may support research but must not be required to run a pipeline.

These backend requirements are design contracts; most are not enforced by the present scaffold.

## Data and model contributions

Use tiny synthetic fixtures that you have permission to redistribute. Do not commit raw customer scans, large binaries, credentials, or downloaded model weights. Use manifests and external storage for datasets and checkpoint bundles.

For ML changes, include the dataset snapshot, grouping/split policy, preprocessing version, random seed, configuration, code revision, baseline comparison, and relevant error slices. Record failed CAD fits and abstentions in the denominator. Report measured geometry and topology metrics; render quality alone is insufficient.

The [ML pipeline guide](development/ML_PIPELINE.md) describes evaluation and promotion requirements. The [CFD guide](docs/CFD_GUIDE.md) describes downstream geometry and simulation checks.

## Validation

Run from the repository root in the virtual environment:

```bash
python -m pytest
python -m ruff check .
python -m ruff format --check .
python -m build
```

CLI changes need coverage for relevant valid commands, invalid values, exit codes, and file side effects. Backend tests should verify real contracts: metre/unit conversion, transform direction, family split leakage, CAD solid validity, topology preservation, reproducible artifact loading, and failure reports. Avoid tests that merely reproduce implementation details.

Large GPU training, native CAD integration, and solver tests are future opt-in suites. They are not performed by the scaffold CI. When adding one, document its environment, fixture source, runtime, and pass criteria.

## Documentation and pull requests

Update command help, the [CLI reference](docs/CLI_REFERENCE.md#cli-reference), examples, and status claims together. Do not add a success badge or benchmark without reproducible evidence.

A pull request should state the problem, the new behavior, validation performed, and any remaining limitations. For design changes, describe the chosen approach, alternatives, and consequences. Avoid claiming that a passing geometry check establishes validated CFD predictions.

Report bugs with the command, package/platform versions, sanitized logs, expected behavior, and a minimal permitted input when relevant. Use [GitHub Issues](https://github.com/jackpitts/Scan2Flow/issues) for ordinary defects and feature discussions.
